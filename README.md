# ESP32 Linker Script Editor

ESP32 / ESP32-S3 の GNU ld リンカスクリプトを読み込み、メモリ領域と出力セクションの対応を確認・編集するデスクトップツールです。Python 標準ライブラリの Tkinter で動作し、追加の pip パッケージやネットワーク接続は不要です。

## 起動

Python 3.11 以降と Tkinter が必要です。Windows ではこのフォルダーの `launch.cmd` を開くか、プロジェクト直下から次を実行します。

```powershell
python tool/ESP32_LinkerScriptEditor/main.py
```

このプロジェクトのビルド済みスクリプトと MAP ファイルを指定して起動する例です。まだ `build` に生成物がない場合は、先に ESP-IDF でビルドしてください。

```powershell
python tool/ESP32_LinkerScriptEditor/main.py `
  build/esp-idf/esp_system/ld/memory.ld `
  build/esp-idf/esp_system/ld/sections.ld `
  --map build/first_sample.map
```

ESP32-S3 の新規テンプレートから始める場合:

```powershell
python tool/ESP32_LinkerScriptEditor/main.py --chip ESP32-S3
```

Tkinter の有無は `python -m tkinter` で確認できます。Linux で Tkinter が含まれていない場合は、使用している Python に対応する OS パッケージを導入してください。

## 基本操作

1. 「build を開く」でビルドフォルダーを選択するか、「.ld を開く」で `memory.ld` と `sections.ld` を読み込みます。ESP-IDF ではメモリ定義と配置ルールが別ファイルになっているため、両方を読み込んでください。build フォルダー内の対応する MAP が特定できた場合は、同時に読み込みます。
2. 右上に表示されるチップ種別を確認します。既存スクリプトから判別できる場合は自動で切り替わります。「新規」では ESP32 / ESP32-S3 のテンプレートを選択できます。
3. メモリ図の領域またはセクションを選択し、右側で開始アドレス・長さ、配置先・本文を編集して反映します。出力セクションを別の領域カードへドラッグしても配置先を変更できます。領域カード右下の「↔ 容量」を左右にドラッグすると、長さを **16 バイト単位**で変更できます。正確な長さは右側の `LENGTH` 欄に入力してください。
4. 「配置ルール」タブで全出力セクションを確認できます。領域カードに収まらないセクションも、この一覧から選択して右側の「選択領域へ移動」で変更できます。「＋ 領域」「＋ セクション」では追加先のファイルを指定して新しく作成できます。
5. 「MAP を読込」で同じビルドの `.map` を読み込むと、出力セクションの実アドレス・サイズを表示します。「コード / オブジェクト (MAP)」タブで入力セクション／オブジェクト／シンボルを確認できます。「全セクションから検索」を選び、例えば `led_blink_task` と入力すると、所属する出力セクションを探せます。
6. 「ソース」と「診断 / チップ情報」を確認し、「.ld を出力」で出力先フォルダーを選びます。読み込み中の全スクリプトを元のファイル名で出力します。作業途中の状態は「編集を保存」でプロジェクト JSON として保存できます。

領域の長さには `128K`、`4M`、開始アドレスには `0x40080000` などを使用できます。式の解決に必要な定義が不足している場合、数値は未解決として表示されます。未知の値を 0 バイトとして扱うことはありません。

「戻す」「やり直す」で編集履歴をたどれます。ソースを直接編集した場合は「ソースの変更を反映」でメモリ図に反映してください。未反映のソースがある状態で別の操作を選ぶと、反映するか確認されます。そこで「はい」を選んだ場合はソースの反映だけを行うので、続けたかった操作をもう一度選んでください。

プロジェクト JSON にはチップ、各スクリプトの本文、MAP 本文と読み込み時の状態、`INCLUDE` の解決に使用する元ファイルのパスを保存します。元ファイルが移動しても保存済み本文は開けますが、未読込の `INCLUDE` を追加するには参照先を指定し直す必要があります。

新規作成・build／プロジェクトの読み込み・終了時の未保存確認は「変更を保存しますか？」に統一しています。「はい」は保存して続行、「いいえ」は保存せずに続行、「キャンセル」は操作を中止します。「いいえ」で終了すると、未反映のソース編集も破棄します。続くファイル選択などをキャンセルした場合は現在の編集を残します。「はい」の後で保存先の選択をキャンセルした場合や保存に失敗した場合は、元の操作を続行しません。

## 配置ルールと実配置の違い

`.ld` は「どの入力セクションを、どの出力セクション／領域に配置するか」を指定します。リンクするオブジェクトがないと、個々の関数やセクションの実サイズは確定しません。このツールはリンカーの代わりにサイズを推測しません。

`.map` の情報は、その MAP ファイルを生成した時点のビルド結果です。配置先や領域サイズを編集しても MAP のアドレスは再計算されません。編集後は「編集前の参考値」と表示され、使用量バーの実配置表示は停止します。対象プロジェクトを再リンクして生成された MAP を読み込み直してください。セクションの移動によって必要になるアラインメント、リテラル配置、到達可能範囲、起動処理の条件などの最終確認も実際のリンカーで行います。

MAP のシンボル行にサイズがない場合、サイズ欄には `—` を表示します。入力セクションのサイズと、個別の関数・変数のサイズは同じとは限りません。

メモリ図は仮想アドレス空間の表示です。特に ESP32-S3 の IRAM と DRAM は物理 SRAM を共有するため、各領域の容量を足して使用可能な物理 RAM の総量と解釈しないでください。Flash のマッピング範囲も搭載 Flash やアプリパーティションの実容量とは異なります。[ESP32-S3 のメモリ種別](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/memory-types.html)

## 対応範囲

- GNU ld の `MEMORY`、`SECTIONS`、`REGION_ALIAS` を読み込みます。
- メモリ領域の開始アドレス・長さ、出力セクションの `> region`、セクション本文を編集し、領域・セクションを追加できます。
- 配置先の変更は実行時アドレス側の `> region` を対象とし、ロード先の `AT> region` は保持します。
- 固定アドレスやコロン前の `ALIGN(...)` など、明示的なアドレス式を持つセクションはドラッグ／配置先欄から移動できません。「ソース」タブでアドレス指定も含めて編集してください。`/DISCARD/` も移動対象外です。
- 未編集部分のコメント、シンボル定義、`KEEP`、`ASSERT` などは元のソースを保持します。入力全体を別の書式に再生成する方式ではありません。
- `INCLUDE` 先は「ファイル → INCLUDE 参照を追加」で、元ファイルからたどれる参照先を追加できます。見つからない場合は「.ld を開く」で指定してください。参照先がさらに `INCLUDE` を持つ場合は、必要に応じて追加操作を繰り返します。C プリプロセッサや外部コマンドは実行しません。
- 同じファイル名のスクリプトを同時には読み込めません。出力時はファイル名を保持し、`INCLUDE` のパスやディレクトリ構成は自動変更しません。サブディレクトリを参照するスクリプトは、出力後もその構成に合わせて配置してください。
- 未展開の `.ld.in` と ESP-IDF の `.lf` は直接の編集対象ではありません。ESP-IDF が生成した `.ld` を使用してください。
- GNU ld のすべての文法を実装しているわけではありません。未解決の式、未知の配置先、重複やアドレス範囲の問題などは診断を確認し、最終的な正しさは対象ツールチェーンで検証してください。

新規テンプレートは配置設計を始めるためのひな型です。ESP-IDF の起動処理、割り込みベクタ、ROM シンボル、MMU の制約、構成ごとの予約領域をすべて含む代替スクリプトではありません。実プロジェクトの編集では、使用中の ESP-IDF と `sdkconfig` から生成したスクリプトを出発点にしてください。

## ESP-IDF プロジェクトへの適用

`build/esp-idf/esp_system/ld/` のファイルは生成物です。そこへ変更を加えても、後続のビルドで上書きされる場合があります。このツールからの出力だけで、ESP-IDF のビルド設定や永続的な配置ルールが自動更新されることはありません。

継続的に特定の関数・オブジェクト・ライブラリの配置を変える場合は、確認した配置をコンポーネントの `.lf` に反映し、`idf_component_register(... LDFRAGMENTS "配置ファイル.lf")` で登録する方法を検討してください。ESP-IDF はフラグメントと設定から実際の `sections.ld` を生成します。[ESP-IDF リンカスクリプト生成](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/linker-script-generation.html)

## 検証

プロジェクト直下から実行します。

```powershell
python -m unittest discover -s tool/ESP32_LinkerScriptEditor/tests -v
python tool/ESP32_LinkerScriptEditor/main.py --smoke-test
```

単体テストではパース、ソース保持、配置先変更、MAP の読み取りを確認します。ローカルの `build` に実際の生成物が存在する場合は、それらを使う統合テストも実行されます。GUI のスモークテストにはデスクトップ環境が必要です。

対応する Xtensa ツールチェーンが PATH または `build/project_description.json` から見つかる場合は、両チップのテンプレートと編集後の出力を実際にリンクし、配置先の変化を検証します。ツールチェーンがない環境では、この検証だけをスキップします。

GNU ld のメモリ領域と出力セクション割り当ての仕様は [GNU ld: MEMORY](https://sourceware.org/binutils/docs/ld/MEMORY.html) を参照してください。
